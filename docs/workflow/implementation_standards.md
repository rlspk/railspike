# Shared implementation standards

Read and apply this contract before dependent work, on resumption, and at closeout in both staged and one-shot Railspike. One-shot reduces planning handoffs and consolidates records; implementation standards remain the same. This contract does not replace either mode's authorization, branch, artifact, commit, study, or debug rules. Keep evidence proportionate in the current plan, implementation summary, or one-shot record; no additional artifact is required.

## Before dependent work

- Read applicable host instructions and preserve unrelated work. Establish the authorized outcome and file boundary using the selected mode's rules; apply [scope and enhancement policy](../../RAILSPIKE.md#enhancement-requests) before expanding work.
- Inspect existing implementations before creating markup, CSS, behavior, helpers, or API payloads. Identify all existing UI/API surfaces that already render the relevant data and the canonical components/contracts they use. Record relevant source paths and reuse or extension decisions; explain why an existing component cannot fit before creating an equivalent. For documentation work, identify existing instruction and evidence surfaces instead. A mockup or skipped planning step does not substitute for this inspection; a separate component catalog is not required.
- Define completion through ordinary UI/CLI entry, the end-to-end result, required failure/retry recovery, applicable deployment/external verification, and the release or handoff condition. A feature is a releasable vertical slice; label component-only work internal maintenance. When a user or environment is named, state the reported mismatch, the next action the user can take unaided, how they verify success or retry, and the evidence needed in that environment.
- Record material risks with impact, early validation and mitigation; resolve them before dependent implementation. Favor the simplest viable implementation, iterating only when necessary; use existing models/fields instead of schema changes where possible.
- For documentation-only scope, name allowed documentation paths, intended reader outcome, evidence boundary, document completion/correction path, and handoff condition. This authority does not permit application source, tests, CI, deployment, or generated-file changes. Follow the selected mode's scope-change rules if those become necessary.

## Verification and final review

- Complete the recorded outcome through its ordinary entry and required recovery, not only a subsystem or direct route. Replay each reported failure in the relevant user/environment as acceptance evidence. A pass on another supported platform is insufficient; actionable manual recovery guidance may satisfy the condition when automatic support is out of scope. Unverified required recovery remains pending or blocked, not complete.
- Check affected shared consumers and applicable roles, environments, migrations, deployment/release conditions, external systems, and other dependencies within approved scope. Record out-of-scope or irrelevant checks as inapplicable with reasons; an unmet in-scope prerequisite is not inapplicable.
- For documentation work, check document integrity, evidence, links/referenced paths, and authorized file scope, including `git diff --check`. Runtime/UI/deployment/migration/release checks are inapplicable unless the document makes a claim requiring them.
- Record commands, results, omissions, and recovery/next action. Label each check passed, failed, blocked, pending, or inapplicable, explaining every non-pass and identifying reproduced baseline failures. A focused pass does not establish a full-suite pass, an untested environment, or the complete user outcome.
- Before each commit and at closeout, inspect the intended diff for unnecessary duplication, unauthorized scope, and missing documentation; verify only intended files are included. Update relevant documentation and [touched concept entries](../concepts.md#implementation-and-verification). Fix in-scope defects and rerun affected checks; otherwise retain the unresolved status and next action.
- Open the handoff with unverified outcomes, including any named user's recovery condition. Record technical completion separately from commit, merge and publication status. Do not declare completion while required work remains blocked or pending. Preserve incomplete, paused, failed and abandoned records under the selected workflow.

Staged cycles record this evidence through their planning and stage-summary fields; one-shot cycles use their consolidated record. Neither documentation compliance nor a checklist alone proves that an agent followed the instructions or that runtime behavior was tested.
