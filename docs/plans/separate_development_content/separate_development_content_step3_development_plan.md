## Completion Contract
Copy/clone/submodule from `rlspk/railspike` yields the usable product; welcome creates host plans. `rlspk/railspike-dev` owns development records/checks/site. Release requires both published states, working links/site, installation/update/recovery evidence, and preserved local work. No history rewrite, automatic conversion, or new publishing system.

## Key Risks
- **High risk: loss.** Inventory/checksum before copying; preserve revisions/recovery copies. Leave unrelated untracked plans, root notes/logs, and ignored files untouched.
- **High risk: access.** Product API: 404; development: public/apparently empty; CLI: unauthenticated. Confirm visibility/access before publishing. Proposed hosting: development `main` root; verify Pages and legacy-site continuity before removal.
- **High risk: links.** Inventory before migration; repair live references, preserve historical quotations, and distinguish existing checker failures from regressions.

## Execution boundary
After approval: branch, organize/commit approved plans/log, then create summary. Stages target ≤1 hour; split overruns. Commit each stage with its summary; record paired commits before advancing. Final product removal includes its temporary summary; the companion retains the canonical summary and product commit reference. Unresolved risks block dependents.

## Stage 1
- Goal: Preserve the maintainer workspace.
- Dependencies: Approval; verified destinations/access.
- Expected changes: Copy tracked plans/logs, maintainers, research, checks/site and license/provenance; establish companion plan ownership after verification. Preserve product history at its new destination.
- Verification approach: Inventory/checksums, recovery record, readable companion publication before removal.
- Risks or open questions: Inspect destination conflicts first; never overwrite commits or untracked work.
- Canonical components/API contracts touched: Development records; Git history.

## Stage 2
- Goal: Enable maintainer checks and website access.
- Dependencies: Stage 1; hosting access.
- Expected changes: Repair indexes; adapt checks to explicit product checkout; retain three equivalent variants. Publish companion site; update canonical/social URLs; retain legacy-site access.
- Verification approach: All checker variants, Git fixture, live site/assets/links; explicit historical-reference exceptions.
- Risks or open questions: Verify hosting first; failures block source removal.
- Canonical components/API contracts touched: Scripts, website, indexes.

## Stage 3
- Goal: Deliver the lean product and source transition.
- Dependencies: Verified preservation/hosting in Stages 1–2.
- Expected changes: Remove migrated tracked content; repair navigation/logo; update live source URLs. Document old-source copy/submodule migration preserving edits/provenance.
- Verification approach: Inventory/links, copy/clone/submodule fixtures, welcome-to-host-plan walkthrough without companion.
- Risks or open questions: Test old/new URL guards first; preserve unexpected-remote refusal and rollback.
- Canonical components/API contracts touched: README, WELCOME, RAILSPIKE, workflow/recovery guidance.

## Stage 4
- Goal: Release and prove recovery.
- Dependencies: Stage 3 checks; remote access; reviewable changes.
- Expected changes: Publish coordinated states; complete companion summary/guidance; retain recovery material until verified.
- Verification approach: Fresh remote installs contain zero development records/tooling; verify site/links, edit preservation, failed-update recovery, unrelated work/index, and both revisions.
- Risks or open questions: Inspect partial publication; preserve/restore prior states without overwriting later edits; block completion.
- Canonical components/API contracts touched: Both repositories; installation/update/recovery.
